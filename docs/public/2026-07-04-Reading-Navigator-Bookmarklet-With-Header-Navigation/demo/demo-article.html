The Long Now of Reading on the Web

Reading long-form content in a browser is a strange, fragmented experience. We open a tab, read for a while, get interrupted, close the laptop, and come back hours later to a wall of text with no memory of where we stopped. This article exists purely as a fixture for testing a reading-position assistant, so it is deliberately long, varied, and full of the kinds of structures a real article contains.

Below you will find headings at several levels, short and long paragraphs, ordered and unordered lists, blockquotes, code blocks, a data table, a figure, and a button that injects content after the page has loaded. Scroll slowly through some sections and quickly through others to exercise the dwell-time tracking.

1. Orientation and Context

The core problem is loss of orientation. Scroll position alone is a poor proxy for where a reader last spent meaningful attention. A layout shift, a late-loading image, or a font swap can move the content under a fixed scroll offset, and suddenly the restored position is meaningless.

Instead of trusting raw pixels, we track how long readable content dwells inside the middle band of the viewport, while the reader is actually present and not scrolling past. Attention, not position, is the signal.

1.1 The active reading band

The active band is the vertical slice of the viewport where reading actually happens. Content that lingers there while the reader is present accumulates credit. Content that flies past during a fast scroll does not.

Position is where the page is. Attention is where the reader is. These are not the same thing, and conflating them is the original sin of naive scroll restoration.

1.2 Velocity matters

A page can move under the reader at wildly different speeds. Slow scrolling suggests reading; a violent flick suggests searching or skipping. The tracker classifies velocity and scales credit accordingly.

  • Slow drift: full reading credit.
  • Normal scroll: partial credit.
  • Skim: visible-only, little credit.
  • Jump: no credit at all.

2. Segmenting the Page

Before anything can be tracked, the page must be broken into meaningful blocks. Not every element matters. Navigation chrome, footers, and sidebars are noise; the article body is signal.

2.1 What counts as a segment

  1. Headings, which anchor the outline.
  2. Paragraphs, the bulk of prose.
  3. List items, both ordered and unordered.
  4. Blockquotes and pull quotes.
  5. Code blocks, which take longer to read.
  6. Figures and images with captions.
  7. Tables of data.

2.2 A code example

Code blocks deserve a higher reading threshold than prose, because scanning code takes longer per pixel. Here is a representative block:

function classifyVelocity(pxPerSec) {
  if (pxPerSec <= 80) return "slow";
  if (pxPerSec <= 300) return "normal";
  if (pxPerSec <= 1200) return "skim";
  return "jump";
}

// Credit is scaled by the classification above.
const factor = { slow: 1.0, normal: 0.6, skim: 0.12, jump: 0 };

Different block types require different amounts of dwell before we are willing to say a reader has probably read them. Certainty is never claimed.

7. Conclusion

If reading progress was tracked well, closing and reopening this page should let you jump back to roughly where you stopped, with a highlight on the restored block. That is the entire promise: not perfect precision, but a reliable, honest sense of place.
