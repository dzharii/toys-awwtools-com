# LeetPick software requirements specification

## A03 Purpose and intent

LeetCode's Medium and Hard labels describe broad difficulty bands. They do not tell a practicing engineer whether a problem offers a direct, discoverable route to a solution or hides a difficult insight behind a few lines of code. Searching discussions and solution repositories to make that distinction consumes practice time and can reveal the answer before the exercise begins. A short implementation is particularly misleading: recognizing a game invariant, proving a greedy choice, or deriving a mathematical identity may be the entire challenge.

LeetPick reduces that selection cost. It presents a deliberately curated list of officially Medium or Hard problems that a JavaScript engineer can reasonably approach with familiar programming tools. Both finding a valid approach and implementing it must be approachable. A longer direct simulation can be a better fit than a clever one-liner. Selection quality takes precedence over list size, recency, or maintaining an artificial quota of Hard problems.

The user opens a compact practice desk, sees unsolved choices first, and follows a title to LeetCode. Each row contains the official number, title, difficulty, an independently written description of the task, a small premise illustration, and completion status. No hints, algorithms, topic labels that reveal an approach, solutions, or reasoning appear in the practice interface. A random picker removes the remaining decision friction without automatically navigating away.

Completion data stays in the user's browser. The user installs a bookmarklet once, runs it while signed in to LeetCode, and returns automatically to LeetPick with accepted problem IDs. LeetPick validates and merges those IDs into browser-local progress. Repeated imports are safe; an older export never erases existing solved entries. The website needs no LeetCode credentials, server-side account integration, or progress database. The user may also mark a problem solved directly after practicing, avoiding a full sync for a single completion. This one-way local claim is stored separately from LeetCode-reported acceptance, participates in the same filters and picker, and survives older imports. Clearing this site's browser data resets it; a JSON backup supports moving progress between browsers.

The illustrations reduce the effort of scanning unfamiliar titles. A water-holding skyline, a row of word tiles, or matching documents makes the situation recognizable before the user opens the full statement. The artwork explains the task's objects and allowed transformation; it does not explain how to compute the answer efficiently. The same two recurring characters make the collection coherent, while each scene remains specific to its problem. Transparent backgrounds let these compact strips sit directly in both themes without turning the list into a gallery of cards.

LeetPick saves time at three points: discovering suitable exercises, avoiding already completed exercises, and choosing the next exercise. Its value depends on defensible editorial decisions, accurate summaries and examples, and reliable progress transfer. A larger catalog or attractive image cannot compensate for a difficult hidden insight, misleading scene, or lost progress. The interface therefore preserves the familiar list structure, uses readable text, and keeps research evidence outside the practice experience. Downloadable sources, references and an offline entry point let the owner inspect the work, retain it independently, and browse the same collection without a running server.


Static share pages let the user invite a friend into a specific exercise with a short, memorable premise rather than a bare problem URL. Each page pairs an original nerdy joke and fictional profile with the problem identity, existing illustration and direct LeetCode destination. Its matching social image makes the invitation recognizable in messaging apps while keeping solutions out of the conversation.
## B03 Scope and terminology

The release includes a static published website, source repository, readable bookmarklet source, research ledger, this specification, AGENTS.md, 74 individually generated illustrations, four original reference sheets, production records and an offline entry point. Preserve the existing Site identity and access policy when updating; the Site's current policy is public. Medium and Hard always mean LeetCode's observed official classification; approachable is our editorial judgment. Solved means either LeetCode reported an accepted solution or the user explicitly marked it solved in this browser. Preserve this provenance; a manual mark is not evidence of acceptance on LeetCode. Unsolved locally means neither source has recorded completion; it does not assert the user has never solved that problem. A catalog is the reviewed published subset, not a claim to cover all existing qualifying problems. Complete illustration coverage means all 74 entries in this release, including entries hidden by current filters.

No solutions, code execution, submission automation, reverse completion toggles, automatic background synchronization, social accounts, feeds, comments, server progress storage, or reset button are in scope. Static per-problem share pages and native/copy sharing controls are in scope. The research universe includes programming problems across all number ranges. SQL-only, shell-only and paid-only exercises are excluded from this release. Future catalog growth must use the same admission rules.


The product name is LeetPick. Preserve the existing Site identity, deployed origin and legacy browser storage keys during rebranding so current progress and installed bookmarklets keep working. Change visible brand text, titles, sync messages and new backup filenames. Do not move users to a new origin as part of this rename.
## C00 Research admission contract

The assumed practitioner knows JavaScript loops, arrays, strings, numeric sorting, Map, Set, basic linked lists and straightforward tree traversal. Familiarity with advanced algorithm names is not assumed. Rate discovery and implementation independently on a 1-5 scale. Discovery 1 follows the statement literally; 2 requires one local, readily explained observation; 3 requires a substantial invariant or pattern transfer; 4 requires a difficult reduction or proof; 5 requires specialist knowledge. Implementation 1 is direct basic operations; 2 is modest bookkeeping or a conventional traversal; 3 adds intricate state or custom structures; 4-5 entail substantial algorithmic machinery. Admit only entries scoring at most 2 on both dimensions.

For every candidate, verify the official ID, title, slug, difficulty, access level and constraints against LeetCode when accessible. Inspect at least one complete implementation written by a solution author and its explanation. Record exact URLs, retrieval date, approach, complexity, language-specific risks, scores, inclusion decision and its reason. A second independent implementation or official editorial is desirable for uncertain cases. Do not call a candidate verified solely from an AI-generated list, search snippet, acceptance percentage, code length, or community vote. If official access is unavailable, record the fallback metadata source and uncertainty explicitly.

Apply this ordered checklist: confirm identity and classification; read the task and constraints; derive the simplest plausible correct route; compare it with a complete published implementation; inspect edge cases and complexity; assess how a human discovers the route before seeing it; assess JavaScript implementation burden; reject hidden leaps; write a spoiler-free summary; record sources and decision. If a simple brute-force solution suffices under the actual constraints, it can qualify even when a more advanced optimization exists. Do not lower either score because the final code is short. Ambiguous cases remain deferred.

Examples: 3195's bounding rectangle is a direct task decomposition and a strong candidate. A vowel game whose answer is a single predicate can still fail discovery review because the game argument is the real work. A Hard problem with a familiar algorithm is not automatically approachable. No Hard entry is admitted merely to populate a filter.

## D01 Research records and coverage

The private research ledger stores admitted and rejected candidates separately from the shipped catalog. Each admitted record includes numeric ID, official title, stable slug, difficulty, original summary, both scores, reasoning, complexity, source URLs and checked date. Source evidence may contain spoilers and must never be copied into the practice UI. Published catalog data contains only ID, title, slug, difficulty, summary and non-revealing audit metadata where needed. Original share-post copy lives separately and must not include solution reasoning.

Record inspected candidates and coverage limitations. The initial catalog is a reviewed edition; exhaustive discovery across the live LeetCode catalog is a continuing research task and must not be advertised as complete. Recheck entries on catalog updates, especially changed difficulty, constraints, access restrictions or broken links. Removing an entry from the catalog must not delete its saved solved ID.

## F00 Random selection

The picker samples uniformly from currently filtered, locally unsolved entries. It respects search and difficulty filters and never returns a solved entry, including when the Solved filter is active. Use crypto.getRandomValues with rejection sampling so modulo bias is avoided. Show the selected title, summary and an explicit Open on LeetCode link. Do not auto-open tabs. Disable or explain the picker when no eligible candidates remain. Selecting again may repeat a problem; do not imply a non-repeating queue.

Use LeetCode's familiar compact problem-list vocabulary and restrained amber difficulty accents without its logo, copied layouts, or assets. LeetPick's own dark visual system uses graphite #20252c, panel #282e36, rule #3b424d, text #edf0f4, secondary #aeb8c5 and amber #f2ba58, with muted green solved indicators. Its light theme uses background #f6f7f9, white panels, text #202b37, secondary #526174 and amber text #805400. Default to dark and persist an explicit theme choice in clearpick.theme, independently of progress. A denied theme write must not interrupt browsing. A system humanist sans stack keeps data dense and readable; tabular numerals align IDs. Use an anchored left editorial rail on wide screens, a single fluid table, and a narrow-screen stacked row treatment. Avoid a marketing hero and repeated cards. Do not display the introductory marketing heading or its description. Keep the established layout, sidebar, picker, controls and independence notice. Use 16px problem titles and 14px summaries on desktop, with 15px titles and 13px summaries on narrow screens. Keep the reviewed-edition badge beside the list metadata.

At widths of at least 1280px, place an unframed illustration after the title/summary cell and before the difficulty and progress cells. Use a 290px column, reduced to 240px through 1390px. Below 1280px, stack the image beneath its description so the text and status columns remain readable; below 741px use the established mobile row layout. Intermediate rows cap illustration width at 420px; mobile illustrations fit the available row width. Preserve the image's 6:1 aspect ratio. Do not reserve a tall gallery area, overlap text, clip controls, or introduce page-level horizontal overflow.

Controls must have visible labels, keyboard focus, semantic buttons and links, and text status in addition to color. Dialogs trap focus natively and restore focus on close. Announce import outcomes and picker results. Honor reduced motion. Support 360px-wide viewports without page-level horizontal scrolling. Filter changes must not move keyboard focus unexpectedly.

Illustrations repeat the task premise already supplied by text and use empty alternative text. They must not be the sole source of a rule or instruction. Every image declares width 960 and height 160, uses lazy loading and asynchronous decoding, and reserves its aspect ratio before loading. Both theme backgrounds must preserve recognizable character fills, relevant objects and readable labels.

On wide layouts with mouse hover, offer the stationary enlarged illustration callout specified in Q00. Keep the existing row sizes and artwork files unchanged. Do not offer this effect in stacked or touch layouts.

The one-way completion action and its reduced-motion, keyboard and touch behavior are defined in S00.

## H01 Bookmarklet export contract

Run only on HTTPS leetcode.com or www.leetcode.com, in the signed-in user's page context. Read the same-origin GraphQL API using the existing session. Reuse the supplied bookmarklet's request pattern: POST /graphql/, Content-Type application/json, credentials same-origin, optional x-csrftoken from csrftoken cookie, and GraphQL error validation. Never export a cookie, token, submission code, user ID, or session ID.

Use the current API observed in the attached network capture: problemsetQuestionListV2, QuestionFilterInput, questions { questionFrontendId status }, totalLength and hasMore. The capture shows SOLVED and TO_DO statuses. Reuse the captured empty filters and category all-code-essentials, paging from skip=0. Query userStatus { isSignedIn username } before collecting and after collecting to detect account changes. Only SOLVED records contribute IDs. Do not use recentAcSubmissionList, because it is a truncated recent history.

Fetch sequential pages of at most 100 records with a short inter-page pause, per-request timeout and bounded retries for network/429/5xx errors. Stop on API/schema errors and never navigate with a partial result. Validate every row, totals, duplicate IDs, pagination progress, upper bounds and stable account identity. If the catalog total changes during export, stop and request a retry. Show a removable progress overlay with Cancel; cancellation aborts requests and leaves the page in place. Prevent concurrent runs. The API is undocumented and may change; explain failures with a retry action and preserve existing LeetPick state.

## I02 Transfer format and routing

Version 1 payload example:

```json
{"version":1,"source":"leetcode.com","username":"example","exportedAt":"2026-11-13T20:00:00.000Z","solvedIds":[48,3195]}
```

IDs are frontend numbers, not internal database IDs. Encode UTF-8 JSON as base64url and navigate to the fixed deployed origin at /#import={payload}. This root hash route avoids static host route fallback requirements and acts as the client-side import endpoint. Never accept a destination from source-page content or imported data. The fragment is not sent as part of the HTTP request; browser history, extensions and script running on the destination can still see it. Strip it with history.replaceState immediately after reading, including on invalid input. Do not send progress to analytics or any server.

Bound decoded JSON to 200,000 characters, at most 20,000 solved IDs, positive safe integer IDs <=1,000,000, username to 100 safe characters and a valid timestamp no more than 24 hours in the future. Validate all fields and version before any write; deduplicate and sort IDs. Reject unsupported versions, malformed encoding, unexpected field types and mixed invalid arrays as a whole. For a generated transfer URL over 60,000 characters, download the identical JSON instead and instruct the user to import it on LeetPick. File import accepts these version 1 transfers and version 2 local backups defined in J01, with a byte-size check before reading. Hash import remains version 1 only.

## J01 Local state and merge semantics

Retain localStorage key clearpick.progress.v1 for compatibility. Read legacy version 1 values without deleting them, then write a validated version 2 envelope on the next successful change. The envelope distinguishes imported evidence from manual claims:

```json
{"version":2,"source":"leetpick","imported":{"version":1,"source":"leetcode.com","username":"example","exportedAt":"2026-11-13T20:00:00.000Z","solvedIds":[48],"lastImportedAt":"2026-11-13T20:01:00.000Z"},"manualSolvedIds":[73]}
```

Before the first account import, imported is null. Never invent a username or export timestamp for manual completion. The effective solved set is the union of imported.solvedIds and manualSolvedIds. Canonicalize both arrays to distinct ascending positive safe integers <=1,000,000, with at most 20,000 combined IDs. Keep unknown catalog IDs. If an imported ID was previously manual, remove its redundant manual entry while retaining its solved state.

Same-account imports union evidence and manual marks monotonically. Older files cannot undo completion. Preserve the newest source exportedAt and update lastImportedAt only when receiving imported evidence. Local-only backups merge manual IDs without changing the active account or its import timestamp. Anonymous manual marks join the first imported account. A different username requires explicit account-switch confirmation; confirmation replaces both the previous account's imported and manual sets, while cancellation preserves both. Recheck the active account before committing a decision made in another tab. This explicit account replacement is separate from an Unsolve action.

Validate and persist the whole envelope before changing in-memory state, showing success or celebrating. Keep prior progress on failure. Serialize read-modify-write operations with an origin-scoped Web Lock on HTTPS where supported, re-reading storage within the lock; other environments use the same read-before-write behavior without a cross-tab atomicity guarantee. Reflect other-tab writes through storage events. Corrupt stored data is not silently erased. Denied storage and quota failures keep browsing available and explain that completion could not be saved.

Export backups in version 2, including both sources and no session material. Accept version 1 and version 2 JSON backups, rejecting invalid input as a whole. Clearing this origin's browser data resets progress; there is no in-product Unsolve or reset control.

## K00 Failure behavior and privacy

An invalid or partial import must leave saved progress unchanged. A failed export must remain on LeetCode. Login failure directs the user to sign in on LeetCode; a schema error reports that the API response changed. Do not attempt security or access-control workarounds. Render imported strings as text, never HTML. Use only validated fixed-origin LeetCode URLs for catalog links. No external fonts, tracking, embeds, credentials, databases or network requests are needed for the practice interface. Site hosting authentication is independent of LeetCode authentication.

Check clipped edges, stray pixels, halos, disappearing strokes and small-label readability against #f6f7f9 and #20252c.

## S00 One-way manual completion and celebration

Unsolved rows expose a semantic button with an accessible problem-specific label. Mouse entry waits 400ms before showing a compact metallic gold frame containing the existing Unsolved label and a party-emoji Solved action. Fade and scale the frame over 140ms; use a 120ms exit grace period so the pointer can reach its button. Keep the callout inside the viewport without reserving row space.
