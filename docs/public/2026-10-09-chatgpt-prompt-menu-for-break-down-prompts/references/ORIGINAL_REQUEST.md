This is a faithful rephrasing of the visible conversation, rather than a verbatim transcript. The initial user message preceding the heap explanation was not included in the supplied context; its design requirements are recoverable from the subsequent complaint and agreed prompt menu.

The user requested an integer heap in C with an almost object-oriented API and a structure containing capacity, count, and items. They wanted technical detail, but the response treated that as a reason to give a lengthy elementary lesson, repeat fields already specified, explain obvious code line by line, add memorization devices, and ask unsolicited textbook questions.

The user specifically rejected manual exercises such as inserting 3 into `[2, 4, 7, 10, 9]` or performing extraction on an example array. They wanted the content and reasoning needed to develop understanding independently, not an assessment of their knowledge. "The complete algorithm on one screen" was an unwanted artificial framing. Its simplified blocks obscured the fact that comparing and swapping repeat in a loop; an illustration that is only intelligible to someone who already knows the heap is a poor explanation.

They asked what instructions or controllable parameters could change verbosity and educational style. The visible conversation concluded that response length, technical depth, assumed knowledge, teaching structure, and intellectual compression should be separate controls. The menu does not reproduce hidden instructions or claim access to hidden tuning parameters. It translates visible preferences into plain-language prompt instructions.

The array discussion explained that completeness makes implicit indexing possible, but did not sufficiently discuss why this representation is practically preferable. The user wanted memory locality, pointer overhead, allocation costs, ownership, and the convenience of a fixed array in automatic storage discussed alongside structural suitability. A dynamically growing array uses allocated storage and still requires cleanup. Pointer-based nodes can also use an arena or automatic storage in appropriate designs. Relative performance depends on layout and access patterns; no universal "pointers are much slower" assertion is encoded into the prompt.

The user found some array/index views and Next-step interactions useful, but the coloring confusing. That attribution is present in the supplied conversation, but the underlying visualization source was not supplied, so it cannot be independently verified here. The product response is an explicit illustration contract: label roles and indexes, explain visual encodings, show repeated comparisons and stopping conditions, and synchronize tree/array states.

The user then asked for an interactive prompt constructor like choosing from a restaurant menu: visible options, pictures, pictograms, icons, and hand-drawn-style illustrations, with default selections and a checklist. The restaurant is an interaction analogy; steak, hamburger, chicken, cooking temperatures, and similar metaphors must not appear in the generated technical prompt. They wanted technical controls such as low/medium/high verbosity and a starting structure they can modify.
